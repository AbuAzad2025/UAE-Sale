# حالة وحدة الصيانة

الوحدة تغطي دورة العمل الكاملة (استقبال ← قطع وخدمات ← فاتورة ← قبض ←
تسليم) مع قيود محاسبية حقيقية، وقد اختُبِرت فعلياً عبر HTTP على خادم محلي
واختبارات منشورة في المستودع. **لا تُعدّ جاهزة للنشر إلا بعد موافقة المستخدم.**

## السياسة المحاسبية المعتمدة

اعتمد المستخدم قرارين:

1. **التسليم الآجل مسموح**: يغلق الأمر على الحساب بعد ترحيل الفاتورة والبقاء
   ضمن حد ائتمان العميل. أما الأمر النقدي فيشترط سداده كاملاً قبل الإغلاق.
2. **تكلفة الأعمال المغطاة بالضمان تُحمَّل على المصروفات**: حساب
   `6401 - مصروف الضمان`، بلا إيراد على العميل وبلا ذمم عليه.
3. **تكلفة العمل (الأجور) تُرحَّل عند إصدار الفاتورة**: مدين `6400 - مصروف
   الصيانة`، دائن `2140 - رواتب مستحقة`. تُسدد عند صرف الرواتب في نظام
   الرواتب القائم.
4. **الدفعة المقدمة عند الاستقبال**: تُنشأ سند قبض مرتبط بالأمر وتُرحَّل
   (مدين الصندوق/البنك، دائن `1131 - ذمم الصيانة مدينة`).

وتفاصيل التنفيذ:

- **القطع** تُصرَف من المخزون بتكلفتها الفعلية (المتوسط المتحرك) لحظة الصرف:
  مدين `5101 - تكلفة الصيانة`، دائن `1140 - المخزون`. يبقى حساب المخزون
  مطابقاً لمذكرة المخزون، ولا يُشطب المخزون إلا بصرف أو إرجاع حقيقي.
- **الإيراد والضريبة** يُعترف بهما عند ترحيل فاتورة الصيانة: مدين
  `1131 - ذمم الصيانة مدينة`، دائن `4210 - إيرادات الصيانة` (صافي)، دائن
  `2131 - ضريبة القيمة المضافة - مخرجات`.
- **الخصم** يخصم من الإيراد: يخفض الأساس الخاضع للضريبة، فتنخفض الضريبة معه.
- **القبض** يقيد: مدين الصندوق/البنك/الشيكات، دائن `1131`.
- **المحرك الحسابي** `services/maintenance_pricing.py` يدعم السعر الشامل
  وغير الشامل، والمعالجات (standard/zero/exempt)، وتوزيع الخصم على البنود
  بتوزيع البواقي (largest remainder) بحيث لا يضيع مليم.
- **الإرسال الآمن للقيود**: كل ترحيل مرتبط بمرجع المستند، ويُ rifiut الترحيل
  الثاني لنفس المستند. العمليات كلها ذرّية (`@tx`).
- **إشعار الدائن** (`maintenance_credit_note`): يُعكس إيراد وضريبة الفاتورة
  ويُتيح المرتجع بعد إصدار الفاتورة.

## ما هو مفعّل وما هو موقوف

- مفعّل ومختبر: الاستقبال، تعديل الحالات، إضافة القطع (مع صرف وقيد)، إضافة
  الخدمات، الخصم، الكفالة، إصدار الفاتورة وترحيلها، القبض (بما فيها دفعة
  مقدمة)، الإغلاق حسب السياسة، المرتجعات (بما في ذلك بعد فاتورة+سند ائتماني)،
  فحص الجودة، وقت الإصلاح، الإعدادات، الخدمات الثابتة، سجل الأجهزة، شراء
  قطع الصيانة من المورد (أمر شراء ← استلام ← ذمم دائنة صيانة `2111` ← سداد)،
  الإشعارات (المزوّد الحقيقي يحدد النتيجة: يُبلَّغ الإرسال أو الفشل كما هو)،
  الطباعة، تقرير التكاليف.
- **موقوف**: لا شيء حالياً - جميع عمليات الاستقبال والمالية والتكلفة والتقارير
  مفعّلة.

## العزل والصلاحيات

- الأدوار المنفصلة: `maintenance_receive` (استقبال وإنشاء أمر)،
  `maintenance_work` (تنفيذ وصرف قطع)، `maintenance_cashier` (تحصيل)،
  `maintenance_close` (إصدار فاتورة وإغلاق وتسليم)، `maintenance_discount`
  (خصم)، `maintenance_settings` (إعدادات وسجل أجهزة)، `maintenance_purchase`
  (شراء قطع الصيانة). في التثبيت الجديد تُمنح هذه الصلاحيات تلقائياً لدور
  `manager` (كلها) و`cashier` (عرض + تحصيل) و`inventory` (عرض + تنفيذ) و
  `accountant` (عرض فقط). الأدوار الموجودة مسبقاً لا تُمسّ؛امنحها من محرر
  الأدوار في لوحة المالك.
- كل مسار صيانة يتطلب سياق تينانت صريحاً؛ لا يُشتق التينانت من معرّف
  المستخدم، ومالك المنصة يحتاج اختيار تينانت (الانتحال) ليعمل.
- `utils/feature_guards.py` يفشل مغلقاً (503) إذا تعذّر التحقق من الميزة.
- الاستعلامات مفلترة بالمستأجر في كل قراءة، والكتابة ترث المستأجر النشط
  ولا يمكن تغيير `tenant_id` لغير المالك.
- كتابة سجل الأجهزة (التي تمنح ضماناً مجانياً) تتطلب صلاحية
  `maintenance_settings` لا `maintenance_view`.
- سجلات الحالة وتدقيق الضمان محمية عند المصدر (ORM) وعند قاعدة البيانات
  (`b33`: UPDATE/DELETE/TRUNCATE). ليست حماية WORM: مسؤول قاعدة البيانات
  المخوّل يستطيع تعطيل المحفزات.

## الاختبارات

- `tests/security/test_maintenance_safety.py`: عزل، IDOR، CSRF، بوابة
  الميزة، ذرّية التدقيق، حماية سجلات التدقيق، استرداد الإيداع.
- `tests/security/test_maintenance_finance.py`: دورة مالية كاملة عبر HTTP مع
  فحص القيود (تكلفة فعلية، إيراد صافي، ضريبة مفصولة، ذمم، قبض، تسليم آجل
  ونقدي، حد الائتمان، الضمان، المرتجعات، شراء القطع من المورد، سند ائتماني،
  منع الترحيل المكرر، توازن القيود).
- `tests/unit/test_maintenance_pricing.py`: محرك التسعير والضريبة.
- `tests/security/test_test_database_guard.py`: تجهيز الاختبارات لا يحذف مخطط
  قاعدة تطوير.
- **فحص مسار المتصفح** (خادم عامل حقيقي + CSRF + كوكيز):
  `tests/manual/maint_ui_seed.py` يبني قاعدة SQLite مؤقتة، ثم شغّل الخادم
  عليها (`DATABASE_URL=sqlite:///<file> python app.py`)، ثم
  `tests/manual/maint_ui_smoke.py` (المتغير `MAINT_UI_BASE` و`MAINT_UI_DB`)
  يمشي على: استقبال ← قطعة ← خدمة ← حالات ← فاتورة ← قبض ← تسليم ← طباعة،
  ويفحص دفتر الأستاذ خلفه. القاعدة المؤقتة تُحذف بعد الفحص.

```powershell
$env:DATABASE_URL = 'sqlite:///:memory:'
python -m pytest tests/security/test_maintenance_safety.py tests/security/test_maintenance_finance.py tests/security/test_test_database_guard.py tests/unit/test_maintenance_pricing.py -q
```

**تحذير:** تجهيز الاختبارات العام في `tests/conftest.py` يحذف مخطط `public`
على PostgreSQL. يرفض الآن قاعدة `ERP-lite`، ويشترط
`ALLOW_DESTRUCTIVE_POSTGRES_TESTS=1` لقاعدة مخصصة للاختبار، و
`ALLOW_DESTRUCTIVE_SQLITE_TESTS=1` لملف SQLite.

## الهجرات

`b31` تكاليف البنود، `b32` عمود الملاحظات الناقص، `b33` حماية سجلات التدقيق،
`b34` حساب مصروف الضمان، `b35` كميات المرتجع، `b36` مدفوعات الموردين،
`b37` سندات الائتمان. مطبَّقة على `ERP-lite` بعد اختبار كل هجرة على جداول
مؤقتة في `tests/manual/`. هذه الاختبارات لا تغطي بقية سلسلة الهجرات ولا
تراجع قاعدة المستخدم الحقيقية.
